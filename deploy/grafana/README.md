# Grafana dashboard for metric summary tables

`dashboard.json` provides a host filter, separate Distribution/Counter/Gauge metric selectors, and nine data panels. All SQL reads `metrics_summary.distributions` or `metrics_summary.counters` directly. Change those database qualifiers and the datasource default if you configure another database. The nine series labels are `host`, `pod`, `instance`, `tag`, `thread`, `uid`, `statusCode`, `mount_name`, and `io`; legends encode the metric name and all nine values as a JSON tuple so quoted values and separators do not collide.

Counter increments and integer Gauge snapshots share the `counters` table (`metricName`, `TIMESTAMP`, `val`). Use different metric names for Counter and Gauge instruments, including across producers. Both selectors list the same table inventory; choose the appropriate instrument's name yourself. No stored kind marker can select it automatically. The supplied examples omit `type` and distribution `method`, so those columns use their empty-string defaults. If your application supplies them as labels, include them in the queries' series identity as well.

Distribution values use nanoseconds for latency metrics; no automatic unit conversion occurs. Panels display the sum of stored `count`, the sample-weighted mean `sum(mean * count) / sum(count)`, mean/worst local-window p99, and maximum. The coverage table includes the observed minimum and mean/worst local-window p95. Percentile summaries cannot reconstruct a global percentile. Adapt the display units for non-latency distributions.

Counter rates are **observed rates over adaptive buckets**: `sum(toFloat64(val)) / toFloat64(bucket_seconds)`. The divisor is always the actual bucket width. These are not per-collection rates: the table stores neither duration nor source sequence. Buckets start at the selected range's beginning; the final bucket may cover a shorter observed period while retaining the full-width divisor. Missing buckets are not filled with zeros, and later increments cannot recover lost batches. Points are not connected across gaps.

All seven time-series panels share the same per-query **50,000 numeric point budget** (`max_points` in each SQL statement). Each query counts the distinct selected metric names and complete nine-label identities in the requested time range. The Gauge panel counts its mean, minimum and maximum separately (`value_columns = 3`); other panels use one value. The query divides the point budget by `series_count * value_columns`, then selects a bucket width at least ten seconds, at least Grafana's interval rounded up to whole seconds, and wide enough to keep every selected series within that budget. It includes the time filter's right endpoint in this calculation. Grafana's `maxDataPoints` alone does not enforce a budget across all series.

No series is removed by a `LIMIT`, Top N selection or label aggregation. If even one point per complete series would exceed the budget, the panel fails explicitly and asks you to narrow the host, metric or time filters. Empty selections return no rows. All read queries retain the database account's separate **100,000 result-row limit**, with overflow errors rather than truncation; the two coverage tables remain subject to that hard limit. Increase `max_points` only together with an explicit assessment of the database and browser limits.

Adaptive sizing adds a `uniqExact` scan of the same selected data for each panel; the main aggregation then reads those rows again. This trades extra read work for bounded output without dropping label identities. A post-grouping `QUALIFY` guard also checks the actual result's point count, so newly inserted series between the two reads cannot bypass the budget; such a query fails explicitly and can be retried. The existing query time and memory limits still apply, so very broad or high-cardinality queries can fail rather than overrun those limits. Use narrower filters for finer resolution. The buckets use integer Unix-millisecond arithmetic anchored at the range start, avoiding ClickHouse's constant-interval argument restrictions; the official plugin expands `$__interval_ms`, `$__fromTime_ms`, and `$__toTime_ms` to numeric interval and timestamp expressions.

Gauge panels show the observed mean, minimum and maximum, plus the most recent observed timestamp in the coverage table. `TIMESTAMP` has one-second precision and stores no sequence or session identity. Same-second values cannot be reliably ordered, so these panels do not claim an exact latest Gauge value or separate producer restarts with identical labels. Repeated stored rows affect sums and means: the ClickHouse MergeTree tables provide no batch or row deduplication, and these queries do not use `FINAL`.

Install the official `grafana-clickhouse-datasource` plugin, pinned to the tested **4.20.0** release. The plugin declares Grafana **11.6.0 or newer**; the actual backend/API validation here used **Grafana 13.2.2** and **ClickHouse 26.8.6.5**. Other combinations require your own validation. The plugin package is available from [Grafana's official download endpoint](https://grafana.com/api/plugins/grafana-clickhouse-datasource/versions/4.20.0/download?os=linux&arch=amd64).

1. Apply `deploy/clickhouse/schema.sql` and execute `readonly-user.sql` as an access-management administrator, binding `grafana_password` from your secret manager. It grants SELECT on only the two summary tables. The account has `readonly=1`; only its query timeout is changeable, within the specified limit. Do not use the collector's writer account in Grafana.
2. Copy `provisioning/datasources/metrics-summary.yml` to Grafana's datasource provisioning directory. Set `GRAFANA_CLICKHOUSE_HOST` and `GRAFANA_CLICKHOUSE_PASSWORD` in the Grafana service environment. The template uses verified HTTPS on port 8443; adjust the port to your ClickHouse endpoint. For a private CA, enable `jsonData.tlsAuthWithCACert` and provide the PEM certificate as `secureJsonData.tlsCACert`. Keep `tlsSkipVerify=false`.
3. Copy `provisioning/dashboards/metrics-summary.yml` to Grafana's dashboard provisioning directory and copy `dashboard.json` to `/var/lib/grafana/dashboards/metrics-summary/`. Adapt the absolute path when deploying containers. Restart Grafana and check datasource health. The dashboard is provisioned as read-only; edit the JSON in version control.
4. Open **Metrics summary — host summaries**, select hosts and the correct metric name for each instrument. If you renamed the ClickHouse database, replace the fixed `metrics_summary.` qualifiers in the JSON and the grants. Grafana environment substitution applies to provisioning files, not dashboard JSON.

Password provisioning deliberately uses `$GRAFANA_CLICKHOUSE_PASSWORD`, avoiding the second expansion that `${...}` can cause for passwords containing `$`. Store the service environment/secret files outside the repository with restricted permissions. Grafana viewers can submit SQL through the datasource, so database privileges, separate database accounts/views when required, and query resource limits provide the security boundary; dashboard filters do not provide tenant isolation.

This dashboard targets the supplied nine-label schema; the summary crates do not enforce that set of keys. If your application writes additional label columns, extend both the series-count and legend tuples, every `GROUP BY`, and the coverage tables with those columns before using this dashboard; otherwise distinct label series would be combined. A table column existing on its own does not automatically add it to these series expressions.

Variable queries return a hexadecimal ID plus the original display text. Queries decode the selected IDs using `unhex`, so names containing quotes or backslashes never need to be inserted as raw SQL labels. Dropdown queries are capped at 10,000 distinct values in the chosen range; narrow host/time scope if your inventory exceeds that. The database profile bounds query runtime, memory, and result rows and fails rather than silently truncating results. Empty histogram windows have no rows; the panels leave gaps instead of displaying fabricated zeros.

## Reproduce verification

The SQL check creates fixture rows and a read-only user in a **disposable loopback server**. It must not run against a real metrics database:

```sh
deploy/clickhouse/run-local-tests.sh /absolute/path/to/clickhouse \
  python3 deploy/grafana/verify.py --disposable
```

To verify the actual plugin, download the official Grafana 13.2.2 distribution and the plugin ZIP above, extract Grafana outside the repository, then run:

```sh
deploy/clickhouse/run-local-tests.sh /absolute/path/to/clickhouse \
  python3 deploy/grafana/verify.py --disposable \
  --grafana-home /absolute/path/to/grafana \
  --plugin-zip /absolute/path/to/grafana-clickhouse-datasource-4.20.0.zip
```

The script binds Grafana to loopback, disables reporting, update checks, news, automatic plugin installation, and public-key retrieval, and removes its temporary data on exit. The signed plugin is loaded normally; unsigned-plugin bypasses are not enabled. Its temporary datasource uses plaintext only to the isolated loopback ClickHouse. The production provisioning template uses HTTPS.

Validation covers all four variable queries and nine panel queries against actual ClickHouse, quoted/backslash-containing hosts and labels, each of the nine label dimensions independently, visible duplicate inserts, count-weighted means, min/p95 and local p99 calculations, adaptive Counter rates with a missing bucket, same-second Gauge ranges, unused `method`/`type` defaults, and read-only rejection of DDL. Generated scale fixtures exercise all seven time-series panels with **200/500/1,000 hosts over 1h/24h**, including two Counter tag series per host. They verify complete identities, every expected bucket and rate, the unchanged read-only row cap, all three Gauge value columns, empty and single-timestamp ranges, sub-second boundaries, the inclusive right endpoint, and a fractional-second Grafana interval. Exact-budget fixtures allow the last fitting series and reject the first excess series explicitly; an intentionally underestimated cardinality also verifies the final actual-output guard.

The optional Grafana run additionally verifies datasource health, file provisioning, dashboard API import, all thirteen fixture variable/panel queries, and eighteen large Histogram/Counter/Gauge queries through Grafana's real plugin macro expansion and result-frame conversion. It checks every selected series and the numeric point count in the resulting frames. The scale test creates roughly 7.2 million temporary metric rows; allow several minutes on a shared machine. Browser rendering and interactive dropdown operation are not asserted by these API checks.

The target fields were checked against the [official 4.20.0 SQL query types](https://github.com/grafana/clickhouse-datasource/blob/v4.20.0/src/types/sql.ts), the adaptive result guard against [ClickHouse QUALIFY](https://clickhouse.com/docs/sql-reference/statements/select/qualify), the macros against the [official macro implementation](https://github.com/grafana/clickhouse-datasource/blob/v4.20.0/pkg/macros/macros.go), and the ID/display-text variable convention against [CHDatasource.metricFindQuery](https://github.com/grafana/clickhouse-datasource/blob/v4.20.0/src/data/CHDatasource.ts). Provisioning and read-only settings follow the [official ClickHouse plugin configuration](https://grafana.com/docs/plugins/grafana-clickhouse-datasource/latest/configure/) and [Grafana provisioning documentation](https://grafana.com/docs/grafana/latest/administration/provisioning/).
