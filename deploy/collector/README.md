# Collector deployment

Build `cargo build --release -p metrics-summary-collector --features tcp`. Apply the ClickHouse DDL under `deploy/clickhouse/` before starting the service. Validate the supplied configuration with `metrics-summary-collector --config deploy/collector/collector.toml --check-config`.

Listeners are opt-in: specify at least one of `http_listen` or `tcp_listen` at the top level of the TOML file. An omitted listener is disabled. The supplied template enables direct HTTP on `0.0.0.0:9091`; uncomment `tcp_listen = "0.0.0.0:9092"` to enable both. You can bind any configured address, including a private IP or loopback. For a TCP-only service, remove `http_listen`, set `tcp_listen`, and build with `cargo build --release -p metrics-summary-collector --no-default-features --features tcp`. HTTP-only builds use the default features. Configuring a listener whose Cargo feature is disabled fails validation. A TCP-only service has no HTTP health or diagnostics endpoints.

Set `METRICS_COLLECTOR_TOKEN` and optionally `CLICKHOUSE_PASSWORD` using the service manager's credential or secret facility, then start `metrics-summary-collector --config /etc/metrics-summary/collector.toml`. The process requires a bearer token. SIGINT/SIGTERM stops admission and drains accepted batches within `shutdown_timeout_ms`; a nonzero exit and structured shutdown report indicate dropped or still unconfirmed batches. Increasing shutdown time cannot replace durable storage.

HTTP ingestion is `POST /v1/batches` with `Content-Type: application/msgpack` and `Authorization: Bearer <token>`. Requests and ACKs use MessagePack with fixed array layouts. Wire v1 rejects compression; histogram fields retain exact `f64` values, and integer fields retain their full signed or unsigned precision. `/healthz` reports process liveness; `/readyz` rejects closing instances. Authenticated `/diagnostics` reports accepted, confirmed, dropped, retries, pending bytes, and oldest pending age. Alert on increasing dropped counts and sustained pending age. Do not interpret Enqueued ACKs as database confirmation.

Each batch carries `timestamp` (signed Unix nanoseconds at collection completion) and `duration_ns` (unsigned monotonic elapsed nanoseconds since the previous collection completed, or since recorder creation for the first collection). A zero duration is valid. The duration describes the statistical interval, not scan, upload, or database execution time. Collector grouping and retries preserve both values; changing either while reusing a batch identity is rejected as conflicting content. Storage maps timestamp to whole-second `TIMESTAMP` and omits duration, batch IDs and source sequence.

Applications can connect directly over HTTP, for example `http://collector.internal:9091/v1/batches`, or over TCP to the configured socket address. Bearer authentication is required for either transport. Plain HTTP and TCP transmit the token and metrics without encryption. TLS is an optional deployment choice: put an HTTPS terminator in front of the collector or use a TCP TLS tunnel when encryption is needed. The collector has no built-in server TLS. HTTPS clients verify the certificate chain and hostname, including when a private CA is configured; HTTP redirect following is disabled.

When using a proxy, forward the Authorization header unchanged and align connection, body-size and timeout limits with the collector. Disable request-body buffering or bound its disk and memory use. A proxy on the same host can forward to a collector bound to loopback; a separate proxy can use the collector's private address. The supplied TCP TLS templates additionally authenticate client certificates and connect the remote sink to a local tunnel socket.

Counter messages carry interval increments, including zero for idle registered counters. Both Counters and Gauges are stored in `metrics_summary.counters` as `metricName`, `TIMESTAMP` and Int64 `val`, with supplied labels as flat columns. Use distinct Counter and Gauge names across producers because storage has no kind marker. Counter increments must fit nonnegative Int64; Gauge values are exact Int64, and fractional, nonfinite or out-of-range facade updates are rejected. Histogram summaries are stored in `distributions` with Float64 count, mean, min, max and p50/p90/p95/p99. Latency observations should be recorded as nanoseconds; unit metadata is not stored and the writer performs no unit conversion. Configure a different database with `[clickhouse] database` if needed.

Retries retain the same protocol batch ID and content, but the ClickHouse tables do not store that identity. The collector's bounded live dedup cache suppresses duplicate submissions while an entry remains. A database retry after an unknown commit, or replay after cache eviction/restart, can insert repeated rows that remain visible and affect aggregation. There are no deduplicating views or `FINAL` guarantees. Counter rates can only be estimated from stored sums over an explicitly chosen time bucket; the per-collection duration is unavailable. Gauge timestamps have second precision, so tied observations cannot identify an exact latest value.

The service assigns its database/table configuration; senders cannot select tables. Application, model version, source attributes, unit, numeric metric IDs, source-session UUID, sequence and duration remain ingestion metadata and are not stored in the ClickHouse tables. `allowed_application` binds the listener's shared token to one application; use separate service instances/tokens for separate trust domains. This is a single-token service, not a multi-tenant authorization server. Rotate the environment secret and restart gracefully.

The receiver reserves capacity for the entire batch before ACK and retains that reservation while writing/retrying. Queued plus in-flight data are capped by `max_pending_batches/max_pending_bytes`; request and connection limits bound receive/ACK states separately. A batch larger than a group is rejected before admission. Configure sender limits so ordinary batches fit all three budgets. MessagePack decoding bounds bytes, structure, rows, labels and strings before allocating the owned payload, then validates the retained model. Malformed layouts, field types, duplicate keys, unsupported versions and trailing data reject the whole message. Budget process memory for `max_requests × max_encoded_bytes` and temporary decoded structures in addition to pending bytes and the bounded dedup cache. Each writer also needs up to the `group_max_encoded_bytes` storage encoding budget (plus allocator capacity); the flat label columns repeat on every stored row. Exact JSON byte counting before admission and grouping prevents accepting a batch that cannot fit the configured storage encoding limit.

Label keys are an end-to-end application/storage convention, with no allowlist or `extra_labels` setting. `host` defaults from `Source.hostname`, and `instance` from `Source.instance`; explicit row labels override either. All other labels are preserved as supplied. Size, count and content validation still apply. Provision compatible string columns in the tables that receive each label and update dashboard grouping to include those dimensions. The CLI passes its resource validation limits to storage and the library rejects mismatched limits. Storage field collisions fail local encoding preflight; actual column existence and types are checked by the writer, so an Enqueued ACK does not promise that an application's column exists. Omitted columns, including distribution `method` and counter `type` unless supplied explicitly, use database defaults.

The defaults use two writer threads, each with its own ClickHouse client, maximum 64 source batches per group and a 100 ms age trigger. No thread is created per request. Confirmation request timeout should exceed group delay plus expected database/retry latency; a timeout reports an unknown outcome and never cancels accepted work. Collector retries have independent time and attempt limits. There is no WAL: process crashes can lose data already acknowledged Enqueued. Storage retries can produce duplicate rows because the storage schema has no deduplication identity; account for this when using the resulting counts.

TCP v1 starts with `MXS1`, a big-endian u16 bearer-token byte length and token bytes (maximum 4096). The server responds `MXS1` or rejects. Each subsequent request and ACK is a big-endian u32 length followed by the same MessagePack payload as HTTP. Frames are bounded before allocation; requests are sequential per connection. Partial frames, deadlines, and EOF discard the connection. Reconnects resend the identical batch ID.

`metrics-summary-collector.service` is a systemd template using a dynamic unprivileged user and a read-only filesystem. Install the executable under `/usr/local/bin`, the TOML under `/etc/metrics-summary`, and a root-owned mode-0600 environment file containing secrets. Adjust `TimeoutStopSec` if you change the collector shutdown budget. The binary uses two Tokio network threads; storage concurrency remains configurable through dedicated writer threads.

The optional `haproxy-server.cfg` terminates HTTPS on 9443 and mutually authenticated TCP TLS on 9444. Its backends use loopback collector sockets; bind the collector to `127.0.0.1:9091` and, if enabled, `127.0.0.1:9092` for this local proxy layout. `haproxy-tcp-client.cfg` provides the sending host's local TCP tunnel on 19092, verifies the collector certificate chain and hostname, and presents a client certificate. Replace example DNS names/certificate paths, provision private keys with mode 0600, and run `haproxy -c -f <config>` before reload. Enable `tcp_listen` and the Cargo `tcp` feature when using the TCP frontend. The HTTPS sender can connect to `https://collector.example.internal:9443/v1/batches` if its certificate chains to a trusted root. For a private HTTPS CA, set `RemoteConfig.tls_ca_pem` or the remote example's `METRICS_COLLECTOR_CA_FILE`; certificate and hostname verification stay enabled. The remote client connects directly to its configured endpoint and does not inherit environment HTTP proxy settings. Retain bearer authentication through both transports. Proxy timeout values must exceed the selected client/collector confirmation budget; update them together when adjusting defaults.

Readiness returns 503 during shutdown or when the pending batch/byte budget is exhausted; it indicates capacity to accept work, not database durability. Liveness only confirms that the process serves requests. Diagnostics and ingestion require the bearer token; probe liveness without placing secrets in URLs. Keep environment files and proxy keys out of source control, readable only by the service manager or relevant service identity. The proxy must not log Authorization headers.

For direct container access, bind the collector to `0.0.0.0:9091` and publish the port with Docker `-p 9091:9091`; publish `9092:9092` as well when TCP is enabled. Supply the TOML and bearer token to the container. With an optional TLS proxy, either share a network namespace and use loopback backends (for example Kubernetes sidecars or Docker `--network container:<collector>`), or place the containers on a shared network and point the proxy at the collector's container address. In the latter layout, bind the collector to `0.0.0.0` or its container interface. A listener bound to container loopback is reachable only within that network namespace; port publishing does not change that. Publish the proxy's TLS ports when TLS is the chosen client entry point.

`/diagnostics` retains `last_write_error` (wall-clock milliseconds, retry class, commit uncertainty, and a controlled reason limited to 1024 UTF-8 bytes) across later recovery. `last_confirmed_unix_ms` tracks the most recent successful group. These fields help distinguish schema, authentication, timeout, and capacity problems after Enqueued ACKs. Built-in ClickHouse errors never include database response bodies or credential-bearing URLs; the collector additionally redacts its ingestion bearer token. Custom injected writers must return credential-free errors and honor the supplied deadline. Failure diagnostics use independent state, without calling a Recorder or emitting per-request logs.

The proxy templates were checked with HAProxy 2.8.28. Reproduce the isolated check with `python3 deploy/collector/test-tls.py /absolute/path/to/haproxy`. It creates temporary certificates and loopback listeners, checks both configurations with `haproxy -c`, and verifies HTTPS certificate trust, unchanged Bearer and `application/msgpack` forwarding, oversize request rejection, opaque TCP bytes through mutual TLS, and rejection without a client certificate. Its echo backends do not decode MessagePack or implement collector admission; the Rust integration tests cover actual requests and ACKs. It does not install certificates or change host services.

For a private ClickHouse HTTPS certificate authority, set `[clickhouse] ca_file` to a PEM bundle and use an `https://` endpoint. The collector validates the bounded bundle before startup, and the writer keeps certificate and hostname verification enabled.
